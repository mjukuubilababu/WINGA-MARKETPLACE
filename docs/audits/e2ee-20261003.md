Date: 2026-10-03

Status: **The five implementation findings were remediated and deployed in

The post-deployment re-audit and production acceptance runbook are recorded in
`docs/audits/e2ee-release-20261003.md`. Local/browser test passes do not constitute
independent cryptographic approval or physical-device acceptance.

## Remediation

The original findings below are retained as evidence against the audited commit.
The follow-up fixes do not enable production flags, relax CSP, reset MLS epochs,
remove a persistent disk or mutate production data.

1. The v2 IndexedDB vault moves sealed history, replay/consumption markers and
   retained admission packages into a separate indexed journal. Reads use pages
   of at most 100 records/4 MiB; ordinary snapshots include only one history page.
   Ratchet, outbox, history and replay writes still share one strict-durability,
   revision-checked transaction. The original 2,000-operation write bound and
   2,000-record/32 MiB core bound remain; journal writes also have a 32 MiB batch
   bound. Point lookups retain exact replay and old receipt behavior. Expired
   private admissions are pruned without deleting consumption evidence. The v1
   upgrade moves existing ciphertext atomically, without re-encryption or reset.
2. A signed `replace-retire` operation records a durable absence tombstone under
   the same PostgreSQL transport lock as reservation. An accepted reservation
   cannot be retired. A delayed request cannot resurrect a retired intent. The
   client verifies the unchanged confirmed local MLS epoch, route and absence
   of a membership journal before and after retiring the local intent. Uncertain
   network responses never cause unilateral deletion. The surviving device may
   retire an absent intent when the old peer device is revoked, but account block
   and suspension policy still applies. This operation grants no message access.
3. Only unfinished replacements use reservation-bound packages; accepted
   replacements use fresh directory packages for the next epoch. The actual
   HTTP/browser MLS flow now reaches epoch 3, excludes both retired devices and
   verifies ciphertext and receipts on the current device.
4. Inspection resolves blocked poll entries by saved conversation id before
   directory fallback. Pending replacement target revocation stays blocked.
   An established conversation with a revoked old peer is shown as blocked,
   with fresh replacement controls only for the selected surviving device and
   only when there is no outstanding replacement or account access denial.
5. Signed group polling uses UUID keyset pages of 100 groups with continuation.
   Every page is reauthorized. The client follows all continuations before
   replacing its cached membership state. Insertion behind a cursor is observed
   on the next full sync, without duplicating or skipping pre-existing rows.

### Recovery Scope

Recovery is explicitly bounded to the latest 1,999 messages within 2 MiB, so a
growing local journal cannot prevent staging the recovery capsule. All four
locales disclose this window before backup. Older local history is retained;
restoring a capsule neither deletes it nor downgrades receipt progress. This is
not an unlimited full-history cloud archive or live MLS key backup. Losing this
device can lose history outside that recovery window. Browser storage quota,
local data eviction and export/viewing very large complete histories remain
capacity constraints; journal paging is not a claim of unlimited storage.

## Original Findings

### 1. P1: Per-owner vault exhaustion permanently blocks ongoing chat

Locations: `src/chat/encrypted-vault.js:157`, `src/chat/mls-runtime.mjs:373`.

The aggregate vault permits at most 2,000 records and 32 MiB. Every incoming
message permanently adds a history record and a received/replay marker; outgoing
messages add history as well. Identity, package, pin and group records consume
the same budget. No history pagination, archival/retention or replay-marker
compaction path was found. Once the limit is reached, the next receive cannot
persist its advanced ratchet/history and the next send cannot stage an outbox.
Even staging the recovery capsule can require additional space at this limit.

Evidence: an isolated Edge browser running the actual vault under strict CSP
successfully stored 1,000 small history/received pairs. The following pair failed
with `crypto_vault_snapshot_too_large`; revision and existing records remained
unchanged. Real chat reaches the count sooner because of its additional records.
Atomicity is correct, but there is no liveness recovery from normal growth.

Required change: separate/paginate encrypted history and establish safe bounded
retention for replay markers and old packages. Reserve room for ratchet/outbox
operations and recovery. Do not fix this by blindly deleting replay state or
simply removing the size limits. Test sustained incoming/outgoing traffic across
the old count and byte limits, reload, replay rejection and recovery at capacity.

### 2. P1: Rejected reservation leaves a local intent that freezes sends

Locations: `src/chat/encryption-session.js:237`, `src/chat/encryption-session.js:270`.

Replacement persists its intent before `replace-reserve`, correctly protecting
ambiguous accepted replies. However, a definitive refusal still leaves that
intent. `requireActiveMembership` then rejects all new text/media for the peer
even when the server group is active and no reservation was accepted. A different
target/package cannot be selected because the retained intent binds the old
package; Resume also requires a replacement record that may not exist. An
expired or consumed target package can therefore freeze a previously healthy
conversation indefinitely.

Evidence: the isolated session control-flow fixture returned a definitive 409
`encrypted_package_unavailable` at reservation. The intent remained, a subsequent
send failed with `encrypted_membership_pending`, and no runtime send occurred.

Required change: provide authenticated reconciliation of reservation absence,
with local epoch/journal checks, before allowing retirement of an unaccepted
intent. Do not clear intents on timeouts or uncertain responses. Test definitive
refusal, accepted-but-lost response, replacement retry, retargeting after an
expired package, and a competing tab/transaction at the reconciliation boundary.

### 3. P2: A completed replacement prevents the same initiator replacing again

Location: `src/chat/encryption-session.js:228`.

`replace` selects current group packages whenever the latest replacement was
initiated by this native device, without checking whether that replacement is
already accepted. The poll retains the completed record, and its group packages
represent current selected devices, not a fresh third device. `inspect` offers
the fresh directory device, but `replace` cannot find it and rejects before
attempting a new reservation. Repeated device rotation through the same surviving
device is broken.

Evidence: with a completed replacement in the poll, the control-flow fixture
offered the fresh third device through inspect. Selecting it returned
`encrypted_package_unavailable`; reservation call count remained zero.

Required change: use reservation-bound packages only for an unfinished
replacement; use current unused directory packages for a new epoch. Add real MLS
and HTTP/browser coverage for two consecutive replacements by the same initiator,
exact retries of the second, and exclusion of both retired devices.

### 4. P2: A blocked poll can be presented as active/encrypted in the UI

Locations: `backend/encrypted-conversations.js:93`,
`src/chat/encryption-session.js:159`, `src/chat/encryption-session.js:174`.

A blocked poll entry contains only its id/status. Peer lookup uses creator and
recipient, so it misses this entry. Directory fallback exposes the stored active
group metadata and can return `status: active` with replacement controls, despite
the current membership being blocked. Sends still fail closed, so this is not a
demonstrated ciphertext access bypass. It is an incorrect security state and can
hide a stalled replacement whose target was subsequently revoked.

Evidence: a blocked poll plus active directory metadata returned `active` from
inspect; sending returned `encrypted_access_denied`.

Required change: reconcile by the local conversation route/id before directory
fallback. Distinguish an explicitly permitted revoked-peer replacement from a
blocked in-progress replacement. Test revocation of a replacement target after
reservation, revoked old peer before reservation, account blocks and suspension.

### 5. P2: Groups after the first 100 are never polled

Location: `backend/encrypted-conversations.js:89`.

Encrypted group polling always selects the oldest 100 groups. It returns no
group cursor/continuation and accepts no per-group poll selector. The client
polls this same list on every sync. A device with more than 100 groups therefore
cannot receive encrypted messages or synchronize membership/receipts for later
groups through this transport. Directory metadata does not retrieve their queued
ciphertext, and local sends require membership in the polled list.

Evidence: source inspection of the server SQL, poll payload contract and all
client sync call sites. This boundary was not exercised with 101 authenticated
MLS groups during the audit.

Required change: authorize paginated or explicitly selected conversation polling
with stable ordering and bounded responses. Test at least 101 groups, pending
replacement beyond page one, page continuity, and concurrent insertions.

## Evidence And Limits

Three replacement/status reproductions executed the actual session source in an
isolated VM. Native key-package attestation used actual Ed25519 signatures; the
MLS engine, vault and HTTP transport were controlled fixtures to isolate branch
behavior. These are control-flow proofs, not new MLS cryptographic acceptance
tests. The vault reproduction used the actual browser IndexedDB/WebCrypto code.
No fixture contacted a production API, used production credentials or wrote
production data.

Before the audit, verification passed 95 secure-content Node tests, all 29
strict-CSP browser tests, 144 frontend core checks and 68 frontend behavior tests.
Those suites do not cover these growth and repeated-transition scenarios. No
assertion of independent crypto assurance follows from their passes.

Review also inspected native approval/revocation, signed reservation/acceptance,
MLS Remove+Add and Welcome bindings, ciphertext journals, media AEAD framing,
epoch-scoped historical media access, backup revision/checkpoint checks and
session/account isolation. Mathematical protocol/library review, deployed
encrypted failover, private-bucket acceptance, physical Android behavior and
capacity/load acceptance remain outside this audit's demonstrated evidence.

Existing release gates still apply: complete vault/key loss is not automatically
recoverable through a history-only capsule; admission expiry after reservation
has no automatic rollback; fresh-device historical media recovery needs a
separately reviewed access policy. Do not silently reset epochs or weaken CSP
to work around these limits.
