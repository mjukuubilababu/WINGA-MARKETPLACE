====================================================================
110. AFTER FOUNDATION — FEATURE ROAD
====================================================================

Only after the Architecture & Security Foundation passes acceptance may
Winga begin implementing the complete Conversations product.

Recommended feature order:

FOUNDATION ACCEPTED
        ↓
DIRECT CONVERSATIONS
        ↓
UNIVERSAL INBOX
        ↓
RICH MESSAGE TYPES
        ↓
VOICE / MEDIA
        ↓
COMMERCE CARDS
        ↓
MESSAGE REQUESTS / SAFETY
        ↓
SHOPPING ROOMS
        ↓
COLLABORATIVE COMMERCE
        ↓
PRIVACY-COMPATIBLE INTELLIGENCE
        ↓
GLOBAL / MULTI-REGION EVOLUTION

Do not implement all stages as one giant change.

Each stage must become stable before the next major layer depends on it.

====================================================================
111. DIRECT CONVERSATIONS FIRST
====================================================================

The first user-facing messaging capability should be reliable direct
Person-to-Person conversation.

Do NOT begin with Shopping Rooms.

Direct Conversations validate:

- message transport
- durable persistence
- E2EE
- message ordering
- retries
- reconnect/resume
- multi-device
- unread state
- delivery/read semantics
- media
- notification behavior

before group complexity is introduced.

====================================================================
112. PERSON → PERSON MODEL
====================================================================

Winga Conversations must not permanently model communication as:

Buyer → Seller

Use:

Person/User → Person/User

A Winga account may simultaneously be:

- buyer
- seller
- creator
- curator
- business operator
- room participant

Conversation identity should remain independent of commerce role.

Commerce context explains WHY people are talking.

====================================================================
113. CANONICAL DIRECT CONVERSATION
====================================================================

Direct conversation should have one stable canonical identity.

Conceptual:

DirectConversation

- conversationId
- participantUserA
- participantUserB
- createdAt
- lastActivityAt
- status

Avoid duplicate direct threads between the same canonical participants
unless explicit business requirements justify separate contexts.

If existing Winga messaging already permits multiple threads per product,
audit that behavior before migration.

Do not silently destroy historical semantics.

====================================================================
114. UNIVERSAL INBOX
====================================================================

The messaging destination should become:

INBOX

not:

"Buyer/Seller Chat"

The Inbox should eventually contain:

- direct conversations
- Shopping Rooms
- message requests
- order-related conversations
- business conversations

using one coherent navigation model.

====================================================================
115. INBOX SUMMARY CONTRACT
====================================================================

Inbox should load conversation summaries, NOT entire message histories.

Conceptual:

ConversationSummary

- conversationId
- conversationType
- participant/room identity
- lastMessagePreview
- lastActivityAt
- unreadCount
- contextPreview
- muted
- archived
- requestState

This allows Inbox to scale independently from full conversation history.

====================================================================
116. INBOX ORDERING
====================================================================

Default:

lastActivityAt DESC

New valid message/activity should move the conversation toward the top.

Do not order active conversations only by creation date.

System events that should NOT bump a conversation must be explicitly
classified.

====================================================================
117. INBOX PAGINATION
====================================================================

Do not load every conversation at once.

Use cursor-based pagination.

Requirements:

- stable ordering
- no duplicates
- no skipped conversations
- refresh-safe
- new-message-safe

Large accounts must remain usable with:

10
100
1,000
10,000+

conversations.

====================================================================
118. CONVERSATION HISTORY PAGINATION
====================================================================

Opening a conversation should load a recent window.

Older messages load progressively when the user scrolls upward.

Do not fetch complete conversation history by default.

Cursor/history semantics must remain compatible with:

- E2EE
- multi-device
- deleted/edited events
- replies
- reactions

====================================================================
119. UNREAD MODEL
====================================================================

Unread state must be canonical and multi-device aware.

Do not define unread only as:

"UI badge stored locally."

Track per-user/read position as appropriate.

Example conceptual model:

lastReadSequence

Conversation sequence:
1 ... 800

User read through:
762

Messages after:
763–800

become unread according to message/event type rules.

====================================================================
120. DO NOT CLEAR UNREAD ON RENDER
====================================================================

Opening/rendering Inbox does not automatically mean messages were read.

READ state should occur only when conversation/message visibility satisfies
the defined product rule.

Define this carefully.

Do not create false read receipts.

====================================================================
121. MESSAGE REQUESTS
====================================================================

As Person-to-Person social messaging grows, unsolicited communication must
be controlled.

Support:

REQUESTED
ACCEPTED
DECLINED
BLOCKED

A new/untrusted person may enter:

Message Requests

instead of the primary Inbox.

Existing commerce interactions may have separate trusted-entry rules.

Example:

Buyer explicitly taps "Message Seller"

may create an accepted commerce conversation according to policy.

====================================================================
122. REQUEST ANTI-SPAM
====================================================================

Limit abuse from:

- mass unsolicited messages
- bots
- new accounts
- repeated declined requests
- blocked users
- automation

Use:

rate limits
reputation
request quotas
block/report signals

without requiring plaintext surveillance.

124. TEXT MESSAGE CONTRACT
====================================================================

Text remains the simplest message type.

Requirements:

- UTF-8 / Unicode
- multilingual text

- line breaks
- reasonable size limit
- E2EE
- reply support
- edit/delete preparation
- accessibility

Do not allow unlimited message size.

====================================================================
125. LINKS
====================================================================

Links in private messages should be treated safely.

Consider:

- URL validation
- malicious link warning
- phishing controls
- safe rendering

Do not send private message plaintext to external preview providers without
explicit privacy design.

Server-side unfurling may conflict with E2EE.

====================================================================
126. REPLIES
====================================================================

Implement structured reply relationship:

replyToMessageId

The encrypted payload may include user-visible quoted context.

Server does not need plaintext quote.

If referenced message is unavailable:

show graceful fallback.

Do not break conversation rendering.

====================================================================
127. REACTIONS
====================================================================

Implement reactions as structured events related to a message.

Examples:

🔥

Do not create a normal text message for every reaction.

Reaction state must reconcile across devices.

====================================================================
128. MESSAGE EDITING
====================================================================

If editing is enabled:

represent edit as an explicit versioned event.

Requirements:

- original message identity remains stable
- authorized sender only
- devices reconcile same final version
- edit indicator shown
- server cannot require plaintext

Define editing window/policy separately.

====================================================================
129. MESSAGE DELETION
====================================================================

Support semantics such as:

DELETE FOR ME

and optionally:

DELETE FOR EVERYONE

Understand limitations:

a recipient device may already have decrypted/read/copied content.

Do not promise cryptographic erasure from another person's device.

Deletion is an application-level synchronization request.

====================================================================

131. VOICE RELIABILITY
====================================================================

Recorded voice must not disappear because upload temporarily fails.

- local temporary persistence
- upload progress
- retry

- FAILED state
- manual retry

Only clear local source when safe under product policy.

====================================================================
132. VOICE PLAYBACK
====================================================================

Support efficient:

- duration
- play/pause
- progress
- playback speed future
- waveform optional

Do not download enormous files unnecessarily.

Encrypted media should remain compatible with streaming/chunked playback

====================================================================
133. VOICE TRANSCRIPTION
====================================================================

Transcription is OPTIONAL intelligence.

Messaging must work without it.

Future options:

- on-device transcription
- user-triggered privacy-aware processing

Do not silently send private voice to external AI services.

134. IMAGES

====================================================================

Example:

"Secure messaging unavailable. Retry."

Security downgrade must never be invisible.

====================================================================

conversation ordering.

Permanent divergent ordering is not acceptable.

213. AUTHORIZATION INVARIANT
====================================================================

No unauthorized user/device may fetch:

conversation ciphertext
attachment ciphertext/reference
room state
delivery state

Every fetch/action requires authorization.

214. ENCRYPTION INVARIANT
====================================================================

For content classified as private E2EE conversation content:

Winga backend must not require plaintext in normal operation.

Exceptions require:

explicit documented user action

or separately defined safety/legal mechanism consistent with the security
contract.

====================================================================
215. DEVICE INVARIANT
====================================================================

routing
cryptographic membership

as required by the chosen protocol.

====================================================================

content.
